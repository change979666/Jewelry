## 深挖 #2: Inquiry → Customer → OEM → Quote → Order 业务链

### 攻击点

15 份文档分别设计了这些模块的表和 API，但**没有一条文档描述了它们之间的完整业务链**。

### 模拟真实流程

```
1. 访客填表单 → Inquiry (D1 inquiries)
2. 管理员查看 → Lead Score (AI) → 判断有价值
3. 创建 Customer (D1 customers) ← 从 Inquiry 提取信息
4. 判断客户需求 → 如果是 OEM 需求 → 创建 OEM Project
5. OEM Project → 需求收集 → 产品匹配 → 打样 → 报价
6. 报价被接受 → 生成 Order (D1 commerce_orders)
7. Order → 付款 → 生产 → 发货 → 完成
```

### 每一步的关联检查

| 步骤 | 源 | 目标 | 关联方式 | 当前设计 | 缺失 |
|------|-----|------|---------|---------|------|
| 1→2 | Inquiry | — | Inquiry 自包含 | ✅ inquiries 表 | — |
| 2→3 | Inquiry | Customer | inquiry.customer_id? 还是 customer 从 inquiry 创建？ | ⚠️ 未设计 | inquiries 表需要加 `customer_id` FK |
| 3→4 | Customer | OEM Project | oem_projects.customer_id | ✅ 有 FK | — |
| 4→5 | OEM Project | Requirements/Samples/Quotes | FK | ✅ 有表 | — |
| 5→6 | Quote | Order | 如何转换？ | ❌ 缺失 | Quote → Order 无设计 |
| 6→7 | Order | Shipment | order 状态机 | ⚠️ | Order 只有状态列，无 shipment 表 |

### 关键缺失

**Quote → Order 转换**：客户接受了 OEM 报价。管理员需要把 Quote 转成 Order。当前没有：

- Quote 的 `status` 如何变为 `accepted`？
- 从 Quote 生成 Order 时，Order 应该复制 Quote 的哪些字段？（product/sku/quantity/unit_price/total）
- Order 创建后，Quote 的状态如何关联？（`order_id` FK 回到 quote？还是 quote 标记 `converted_to_order_id`？）
- 如果 Quote 有多个版本（v1 rejected, v2 accepted），Order 引用哪个版本？

### 判定

**🔴 STOP #2: Inquiry→Customer→OEM→Quote→Order 完整业务链未设计。Phase 6 开发前必须完成此链的状态机和关联设计。**

**建议**：
```sql
-- inquiries 加列
ALTER TABLE inquiries ADD COLUMN customer_id TEXT REFERENCES customers(id);
ALTER TABLE inquiries ADD COLUMN converted_to_oem_project_id TEXT;

-- oem_quotes 加列
ALTER TABLE oem_quotes ADD COLUMN status TEXT DEFAULT 'draft';  -- draft|sent|negotiating|accepted|rejected
ALTER TABLE oem_quotes ADD COLUMN converted_to_order_id TEXT;

-- commerce_orders 加列
ALTER TABLE commerce_orders ADD COLUMN source_type TEXT;  -- 'direct'|'oem_quote'|'inquiry'
ALTER TABLE commerce_orders ADD COLUMN source_id TEXT;     -- oem_quote_id or inquiry_id
```

## 深挖 #3: AI Mission / Task / Run / Action — 过度抽象？

### 攻击点

V1 的 AI 执行模型：

```
Mission (ai_missions)
  └── Action (ai_action_logs)
       └── Task Run (task_runs)
            └── Task (tasks)
```

V2 计划新增：

```
ai_tasks (统一任务队列)
ai_automation_rules (WHEN/IF/THEN)
```

### 层数统计

```
一个 AI 动作从触发到完成经过的对象：

触发器 (cron/user/rule)
  → Mission (ai_missions)        ← 第 1 层
    → Task (tasks)               ← 第 2 层
      → Task Run (task_runs)     ← 第 3 层
        → Action (ai_action_logs)← 第 4 层
          → ai_tasks (V2 新增)   ← 第 5 层？
```

**5 层对象，记录同一个 AI 执行。这是过度抽象。**

### 简化方案

```
触发器 (cron/user/rule)
  → ai_task (一张表，取代 tasks + task_runs + ai_tasks)
       │
       ├── task_type, status, permission_level, budget_consumed
       ├── input_snapshot, output_snapshot, diff
       ├── idempotency_key
       ├── retry_count, error_message
       ├── created_at, started_at, completed_at
       └── mission_id → ai_missions (保留，用于日报聚合)
```

**砍掉 `tasks`、`task_runs`、`ai_tasks` 三张表，合并为一张 `ai_tasks`。**

`ai_action_logs` 保留——它是步骤级日志，用于 Mission Replay。但它不应该是独立对象——它应该是 `ai_tasks` 的子记录。

`ai_missions` 保留——它是日报聚合的容器（"今天 AI 做了哪些事"）。

### 最终模型

```
ai_missions (容器: 今天早上 7 点的 cron run)
  └── ai_tasks (具体任务: "优化产品 X 的 SEO")
        ├── status: queued → running → awaiting_approval → completed | failed
        ├── permission_level: L2
        ├── budget_consumed: ¥0.02
        ├── input_snapshot: { before: "...", entity_type: "commerce_product", entity_id: "123" }
        ├── output_snapshot: { after: "...", diff: "..." }
        ├── idempotency_key: "optimize-seo:product:123:2026-08-24"
        ├── retry_count: 0
        └── ai_actions (步骤日志: "call DeepSeek → parse response → truthfulness check → save draft")
```

**3 层 → 2 层。砍掉 tasks、task_runs、ai_tasks 三表合一。**

### 判定

**🟠 MUST FIX BEFORE PHASE 7: AI 执行模型从 5 层简化到 2 层（ai_missions → ai_tasks）。V1 的 tasks/task_runs 数据迁移到 ai_tasks。**

## 深挖 #4: GitHub + D1 + R2 — 谁才是 Source of Truth？

### 攻击点

Aromiso 有三个存储系统：

| 存储 | 内容 | 读写方式 |
|------|------|---------|
| GitHub | 博客/产品资料/指南/案例/FAQ 的 MD 文件 | GitHub Contents API |
| D1 | 商品/SKU/订单/询盘/OEM/AI/视频/增长数据 | SQL |
| R2 | 图片/视频/PDF/证书/本地化图片 | Object PUT/GET/DELETE |

### 三系统之间没有事务

```
场景：用户发布一个产品

1. D1: UPDATE commerce_products SET status='published'     ← 成功
2. GitHub: PUT src/content/products/lavender-oil.en.md     ← 失败 (rate limit)
3. R2: 无需操作（图片已上传）

结果：后台显示「已发布」，前台显示旧版本。不一致。
```

### 什么是真源？

| 数据类型 | 真源 | 副本 |
|---------|------|------|
| 内容（博客/产品资料/指南/案例/FAQ） | **GitHub MD 文件** | D1（无副本，content_versions 只有 metadata） |
| 商品（SKU/价格/库存/MOQ） | **D1 commerce_products** | 无副本 |
| 图片/视频 | **R2** | 无副本 |
| AI 数据 | **D1** | 无副本 |
| 增长数据 | **D1** | 无副本 |

**这个真源定义是清晰的。问题不是「谁是真源」，而是「跨真源操作失败后怎么办」。**

### 每类跨真源操作的处理

| 操作 | 涉及真源 | 失败处理 |
|------|---------|---------|
| 发布博客 | GitHub PUT | GitHub 失败 → D1 不写（没有 D1 副本），返回错误给用户 |
| 发布产品资料 | GitHub PUT | 同上 |
| 修改商品 | D1 UPDATE | D1 失败 → 返回错误 |
| 上传图片 + 关联商品 | R2 PUT + D1 UPDATE | R2 失败 → D1 不写。D1 失败 → R2 图片保留（孤儿，后续清理） |
| AI 修改 SEO | D1 UPDATE (draft) + 等待人工确认 → GitHub PUT | GitHub 失败 → draft 保留，状态标记 publish_failed |
| 删除商品 | D1 UPDATE deleted_at | 单真源，无跨系统 |

### 当前设计缺口

**发布失败的用户可见性**：

当前设计：GitHub PUT 失败 → API 返回 error。但用户不知道「发布失败」意味着什么。是重试？还是联系管理员？

**建议**：
- 每个 publish 操作返回 `publish_status: 'github_committed' | 'github_failed' | 'cf_building' | 'cf_deployed' | 'cf_build_failed'`
- Phase 4 内容中心在列表页显示发布状态徽章（不仅是 Draft/Published，还有 Publishing/Build Failed）
- CF build 状态通过 Deployment Hook 回调写入 D1（或者手动刷新按钮）

### 判定

**🟠 MUST FIX BEFORE PHASE 4: 每个跨真源操作必须有明确的失败状态和处理流程。内容发布状态机必须从二元（Draft/Published）升级到五态（Draft → Committing → Building → Deployed → BuildFailed）。**

## 深挖 #5: AI 修改业务数据的 Approval / Version / Audit / Rollback 闭环

### 攻击点

设计上这四个环节都存在。但实际推演一个完整的 AI 修改 → 回滚流程，看看链路是否真正闭合。

### 模拟

```
1. AI (L2) 优化产品 SEO Description
2. 生成: "Private Label Essential Oil Manufacturer China | Wholesale Bulk"
3. 权限闸: enforceMode('meta_rewrite') → L2 (需要人工确认)
4. 真实性闸: checkClaims() → WARNING: "Manufacturer" — Aromiso 是连接方非制造商
5. 预算闸: consume('meta_rewrite') → ¥0.02, within budget
6. 结果: 写入 ai_tasks (status='awaiting_approval', output_snapshot=新文案, diff=旧→新)
7. 用户看到 Diff: 旧文案 vs 新文案 + ⚠️ 真实性警告 "Manufacturer" 标红
8. 用户点 [Accept]
9. Version: content_versions INSERT (version metadata, 记录此修改)
10. Audit: audit_logs INSERT (who=ai:product_copywriter, what=modified SEO desc, before/after)
11. D1: UPDATE commerce_products SET seo_description='新文案'
12. GitHub: PUT src/content/products/lavender-oil.en.md (更新 frontmatter seo_description)
13. 构建: CF build triggered
```

### 回滚推演

```
用户 3 天后发现 SEO Description 不合适，点 [Rollback]

14. Rollback: 读取 content_versions → 找到修改前的版本 metadata
15. 因为 body_snapshot 已砍掉 → 需要从 GitHub commit history 读旧版 MD 文件
16. GitHub API: GET .../contents/...?ref=<commit-before-ai-change>
17. 提取旧版 seo_description
18. D1: UPDATE commerce_products SET seo_description='旧文案'
19. Audit: audit_logs INSERT (who=human:admin, what=rollback SEO desc)
20. Version: content_versions INSERT (version metadata, 记录 rollback)
21. GitHub: PUT 旧版 MD 文件
```

### 回滚中的问题

**步骤 15-16**：因为 body_snapshot 已砍掉，回滚需要查 GitHub commit history。但：

- 哪个 commit 是「AI 修改之前」的 commit？content_versions 记录了 change_summary 和 created_at，但**没有记录对应的 GitHub commit SHA**。
- GitHub API 需要先查 `git/commits?path=...` 找到对应文件的历史，再根据时间匹配 content_versions 的 created_at → 找到对应的 commit SHA → 再读文件内容。**这是一次 GitHub API 调用变成了 2 次**。

**步骤 21**：回滚 = 重新 PUT 旧版 MD 文件到 GitHub。这产生了一个新 commit。如果用户在回滚后再回滚（undo the rollback），就变成了 commit C → commit D → commit E。GitHub history 变得混乱。

### 修复

**content_versions 必须加 `github_commit_sha` 列**：

```sql
ALTER TABLE content_versions ADD COLUMN github_commit_sha TEXT;
```

每次发布（GitHub PUT）成功后，将返回的 commit SHA 写入 content_versions 的对应行。回滚时直接用 SHA 读文件（1 次 API 调用）。

### 另外的问题：回滚 = 新修改还是真回滚？

**回滚的本质**：把数据恢复到旧状态。但系统实现上，回滚 = 一次新的修改（新 version + 新 audit + 新 GitHub commit）。

这意味着：回滚后 version 列表显示「AI 修改 → 人工回滚」，但**没有「回滚到哪个版本」的明确关联**。如果多次回滚，版本链就断了。

**建议**：content_versions 加 `rollback_to_version_id` 列。回滚时记录「此版本回滚到 version X」。这样版本链是可追溯的。

### 判定

**🟡 SHOULD FIX BEFORE PHASE 7: content_versions 加 `github_commit_sha` 和 `rollback_to_version_id` 两列。回滚链路才算真正闭合。**

# 四、开发者可执行性测试
