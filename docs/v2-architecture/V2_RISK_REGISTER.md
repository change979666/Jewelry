# V2 P0-12: 风险登记册
## Risk Register

> 基于 5 份审计报告 + V2 设计规范 + AGENTS.md
> 日期：2026-08-24

---

## 1. 风险等级定义

| 等级 | 概率 | 影响 | 响应 |
|------|------|------|------|
| 🔴 Critical | 高/中 | 高 | 必须有缓解措施 + 回滚方案，阻塞 Phase 推进 |
| 🟠 High | 中 | 中/高 | 必须有缓解措施，按 Phase 监控 |
| 🟡 Medium | 低 | 中 | 记录追踪，不阻塞开发 |
| 🟢 Low | 低 | 低 | 记录即可 |

## 2. 技术风险

### R1: CF Functions 10s 超时 → 批量操作中断
| 属性 | 值 |
|------|-----|
| 等级 | 🔴 Critical |
| 概率 | 高（批量 > 20 条 AI 操作必定超 10s） |
| 影响 | 批量 AI 优化/翻译/SEO 在同步模式下不可用 |
| 触发条件 | 用户选择 > 5 条内容执行 AI 操作 |
| 缓解 | Phase 7 实现 AI Task Queue（异步）。简单批量（改状态/分类）分批执行（每批 20）。 |
| 回滚 | AI Task Queue 未就绪时，批量操作上限限制为 5 条 |
| Phase | Phase 4（内容批量）+ Phase 7（AI Task Queue） |

### R2: GitHub API rate limit → 内容发布失败
| 属性 | 值 |
|------|-----|
| 等级 | 🟠 High |
| 概率 | 中（5000 req/hour，批量操作可触发） |
| 影响 | 内容无法发布，用户等待时间增加 |
| 触发条件 | 短时间内 > 100 次 GitHub API 调用 |
| 缓解 | 保留现有节流逻辑。批量发布每批 10 条，间隔 5s。加队列重试 3 次。 |
| 回滚 | 降至单条发布，退回到 V1 模式 |
| Phase | Phase 4（批量操作设计时必须考虑） |

### R3: D1 并发限制 → 多用户写入冲突
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 低（当前单用户，V2 多数时间也单用户） |
| 影响 | 写入失败或数据竞争 |
| 触发条件 | 至少 2 个活跃管理员同时写同一对象 |
| 缓解 | V2 乐观锁（version 字段）。WAL 模式已启用。 |
| 回滚 | 降低为「最后一个写入者胜出」 |
| Phase | Phase 2（version 字段引入时） |

### R4: 旧 API 调用方未知 → 兼容路由遗漏
| 属性 | 值 |
|------|-----|
| 等级 | 🟠 High |
| 概率 | 中（可能有外部脚本/cron 调用了未记录的 API） |
| 影响 | 旧调用方在 Phase 14 切换后报错 |
| 触发条件 | Phase 14 下线旧路由时 |
| 缓解 | P0-3 全量 API 审计。30 天观察期（Phase 14 后保留兼容路由 + 日志计数）。 |
| 回滚 | 恢复旧路由 |
| Phase | Phase 14 |

### R5: Astro/React Island 混合 → 构建复杂度失控
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 中（两套组件系统并存增加认知负担） |
| 影响 | 构建变慢、bundle 膨胀、SSR/hydration 边界问题 |
| 触发条件 | React island 数量 > 20 |
| 缓解 | P0-11 组件技术选型原则（优先 Astro，仅复杂交互用 React）。每加一个 React island 需明确理由。 |
| 回滚 | React island 可降级为纯 Astro 组件 |
| Phase | Phase 1 开始持续关注 |

### R6: 软删除迁移 → 现有查询遗漏 `WHERE deleted_at IS NULL`
| 属性 | 值 |
|------|-----|
| 等级 | 🟠 High |
| 概率 | 高（52 张表 + 未来 18 张，逐表加列时容易遗漏查询更新） |
| 影响 | 已删除的数据继续出现在列表（幽灵数据）或正常数据被隐藏 |
| 触发条件 | 对某表加了 `deleted_at` 列但未更新该表的所有 SELECT 查询 |
| 缓解 | 数据访问层统一封装（`src/lib/admin/api/`），所有查询经过 `softDeleteFilter()`。逐表迁移 + 测试。 |
| 回滚 | 移除 `deleted_at` 列，恢复物理删除 |
| Phase | Phase 4（逐表迁移） |

### R7: 组件拆分不完整 → 新旧 UI 不一致
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 中（46 个组件无法一次全部完成） |
| 影响 | 部分页面使用新组件，部分仍用旧内联 UI，体验割裂 |
| 触发条件 | 某模块先迁移到 V2 但该模块的某些子功能未迁移 |
| 缓解 | 每 Phase 完成整个模块的所有页面（不一页一半）。旧页面保留在 `/admin` 不受影响。 |
| 回滚 | 未完成的模块继续使用旧 `/admin` 路由 |
| Phase | Phase 4-13 持续 |

## 3. 数据风险

### R8: OEM 项目从零开始 → 无历史数据
| 属性 | 值 |
|------|-----|
| 等级 | 🟢 Low |
| 概率 | 高 |
| 影响 | OEM 模块初始为空，用户需手动录入历史项目 |
| 触发条件 | Phase 6 OEM 模块上线时 |
| 缓解 | OEM 是全新模块，接受冷启动。可提供 Excel 导入模板。 |
| 回滚 | 无需回滚 |
| Phase | Phase 6 |

### R9: R2 文件非原子删除 → 业务对象删除后文件残留
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 中 |
| 影响 | R2 存储膨胀，废旧文件占用空间 |
| 触发条件 | 用户永久删除商品/内容，但关联的 R2 文件未清理 |
| 缓解 | V2 §30：R2 文件不能因业务对象删除而直接无审计清理。回收站保留 30 天后才清理 R2。 |
| 回滚 | 无需回滚（R2 存储费用极低） |
| Phase | Phase 4（软删除 + 回收站） |

### R10: D1 Migration 执行失败 → 新表不可用
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 低（SQLite DDL 简单） |
| 影响 | 依赖新表的 Phase 无法推进 |
| 触发条件 | Migration 语法错误 / 约束冲突 / 与已有表名冲突 |
| 缓解 | 每次 migration 先在本地 D1 预览验证。P0-4 完成全部已有表清单后再写 migration DDL（确保不与已有表冲突）。 |
| 回滚 | 执行 DOWN migration |
| Phase | Phase 2 开始每次迁移前 |

## 4. 兼容风险

### R11: V2 前端重构期间 → 用户无法正常工作
| 属性 | 值 |
|------|-----|
| 等级 | 🟠 High |
| 概率 | 低（因为有 `/admin` 和 `/admin-v2` 双路由） |
| 影响 | 如果 `/admin` 被不小心破坏，用户丧失所有后台能力 |
| 触发条件 | Phase 1-13 期间意外改动 `/admin` 路径或旧 API |
| 缓解 | 铁律：**V2 开发期 `/admin` 和全部旧 API 完全不改动**（P0-10 §8 锁死清单）。每个 Phase 完成后跑 V1 API 冒烟测试。 |
| 回滚 | git revert + CF 自动部署 |
| Phase | Phase 1-14 全程 |

### R12: 环境变量变化 → 运行时断裂
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 低 |
| 影响 | V2 新功能需要的新环境变量未配置 → API 500 |
| 触发条件 | 新 API 引用了未在 CF Pages Secrets 中配置的环境变量 |
| 缓解 | 每个 Phase 的环境变量需求清单提前列出。先在 `.dev.vars` 验证，再在 CF Dashboard 手动添加。 |
| 回滚 | 添加缺失的环境变量 → 再触发一次部署 |
| Phase | Phase 2 开始 |

## 5. 业务风险

### R13: AI 模型幻觉 → 内容误写
| 属性 | 值 |
|------|-----|
| 等级 | 🟠 High |
| 概率 | 中（LLM 性质） |
| 影响 | 生成的内容包含不实信息（编造认证、统计、价格） |
| 触发条件 | AI 生成对外内容时 |
| 缓解 | **完整复用现有 truthfulness.ts 5 条红线**。所有 L2 内容操作必须人工审核。Diff viewer 让用户看到 AI 改了什么。L3/L4 仅限低风险可逆操作。 |
| 回滚 | AI 修改可回滚（保存旧版本） |
| Phase | Phase 7 |

### R14: AI 预算超支
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium |
| 概率 | 中（AI 功能增加 → 调用量增加） |
| 影响 | API 费用超预期 |
| 触发条件 | 自动化规则 + AI Panel 导致调用量翻倍 |
| 缓解 | **完整复用现有 action-budget.ts 三层预算**。V2 AI Cost Dashboard 实时显示。每 Phase 后检查 AI 调用量变化。 |
| 回滚 | 降低预算上限或关闭部分自动化规则 |
| Phase | Phase 7 开始监控 |

### R15: RBAC 配置错误 → 管理员被锁
| 属性 | 值 |
|------|-----|
| 等级 | 🔴 Critical |
| 概率 | 低（初始设置时可能发生） |
| 影响 | 所有用户无法访问后台 |
| 触发条件 | Owner 角色被误删除或权限被清空 |
| 缓解 | Owner 角色硬编码（代码层保证不可删除、不可降权）。V2 RBAC 中间件在 `admin_users` 为空时自动 fallback 到 V1 `isAuthed()` 模式。 |
| 回滚 | 删除 `admin_users` 表 → 系统自动回退到单密码模式 |
| Phase | Phase 2 |

### R16: 软删除后用户误以为数据丢失
| 属性 | 值 |
|------|-----|
| 等级 | 🟢 Low |
| 概率 | 中 |
| 影响 | 用户困惑、Support 请求 |
| 触发条件 | 用户删除后找不到数据 |
| 缓解 | 删除确认弹窗明确告知「移至回收站，30 天内可恢复」。回收站入口可见。Toast 提示「已移至回收站 → [查看]」。 |
| 回滚 | 无需回滚 |
| Phase | Phase 4 |

## 6. 安全风险

### R17: RBAC 绕过 → 未授权操作
| 属性 | 值 |
|------|-----|
| 等级 | 🔴 Critical |
| 概率 | 低（有 V1 auth 基础 + V2 server-side enforcement） |
| 影响 | 低权限用户执行高权限操作 |
| 触发条件 | RBAC 中间件 bug 或漏加权限检查 |
| 缓解 | V2 §33：**服务端必须做 RBAC，UI 自己决定权限 → 禁止**。每个 API handler 必须调用 `checkPermission(user, action, resource)`。Audit log 记录所有操作供事后审计。 |
| 回滚 | 临时恢复 V1 单密码模式 |
| Phase | Phase 2 |

### R18: AI 提权注入 → permissions.ts 防线被绕过
| 属性 | 值 |
|------|-----|
| 等级 | 🟡 Medium（现有多层防线） |
| 概率 | 低（当前 `enforceMode()` 设计优秀） |
| 影响 | AI 执行了 MANUAL 级别的任务 |
| 触发条件 | 新 task_type 被错误加入 TASK_TYPE_POLICY 并给了过高权限 |
| 缓解 | **铁律：TASK_TYPE_POLICY 新增条目必须 review。未知 task_type = MANUAL（保守默认）。`enforceMode()` 不看 AI 自报的 mode。** |
| 回滚 | 修改 TASK_TYPE_POLICY 或 FORBIDDEN_TASK_TYPES |
| Phase | Phase 7（加新 task_type 时） |

## 7. 进度风险

### R19: 预算/时间超预期
| 属性 | 值 |
|------|-----|
| 等级 | 🟠 High |
| 概率 | 高（14 Phase，每个可能有意外复杂度） |
| 影响 | V2 上线延迟 |
| 触发条件 | 某 Phase 遭遇未预见的复杂度 |
| 缓解 | **每 Phase 独立可运行**——即使后续 Phase 延迟，已完成 Phase 已产生价值。M1-M5 里程碑独立交付。核心价值在 Phase 3-6（Dashboard + Content + Commerce + Customer/OEM）。 |
| 回滚 | 按 Phase 优先级排序，必要时裁减低优先级 Phase |
| Phase | 全周期 |
