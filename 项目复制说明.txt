# Middle East Jewelry DTC V1.0

## Aromiso Commerce OS Fork — 一次性架构定案与开发总指令

> 项目性质：独立于 Aromiso 的全新 B2C Jewelry DTC 项目
> 目标市场：KSA（第一市场）+ UAE（第二市场），架构兼容 GCC
> 首发品类：女性日常轻奢饰品
> 腰带：暂不进入首发商业范围，但底层商品模型不得阻塞未来扩展
> 首发商品规模：20–30 SKU
> 后续商品：持续逐个/小批量上架，不采用 Aromiso 式一次性导入数百/上千 SKU
> 技术策略：Fork Aromiso 成熟 OS，不复制 Aromiso 香薰业务层
> 部署策略：首期优先 Cloudflare Free，严格做资源保护
> 架构策略：本 V1.0 定案后，后续禁止因为“小功能”反复推倒重构

---

# 一、项目总原则

这个项目不是“复制一个 Aromiso 改成卖饰品”。

正确关系：

```text

   │     ├── Astro
   │     ├── Cloudflare
   │     ├── D1
   │     ├── R2
   │     ├── KV
   │     ├── Admin

   │     ├── SEO

   │     ├── AI
   │     ├── Automation
   │     ├── Analytics
   │     ├── Testing
   │     └── Deployment
   │
   └── Aromiso 香薰业务层
           ❌ 不复制


Jewelry
   │
   ├── 继承成熟 OS
   │
   └── 新建 Jewelry Commerce Core
```

核心思想：

> **复制“操作系统”，重建“生意”。**

# 二、项目必须彻底隔离

Jewelry 必须成为完全独立项目。

禁止共享：

* Git repository
* Cloudflare project
* D1 database
* R2 bucket
* KV namespace
* production secrets
* domain
* auth cookies
* production environment variables
* Aromiso business data

允许复制：

Jewelry 项目内部不得出现 Aromiso 品牌、香薰商品、香型、精油、B2B 询盘等业务残留。

# 四、商业定位冻结

品牌不是：

* SHEIN 中国白牌版
* 低价饰品批发站
* Ounass 平替
* “大量中国货铺满网站”

品牌定位：

> 面向 Gulf 年轻女性的日常轻奢设计饰品品牌。

核心价格带：

```text
Entry      SAR 79–129
Core       SAR 149–249
Statement  SAR 299–399
Set/Gift   SAR 249–399
```

战略价格区间是 SAR 99–399，但价格系统不得写死上下限，未来必须允许自然扩展到 SAR 499+。

## 当前调研显示，Namshi 的饰品流量实际上被太阳镜、手表、箱包等占据，站内 jewellery 搜索甚至没有形成有效货架；Ounass 的实测珠宝最低入口约 475 AED；L'azurde 的年轻线最低入口也在 SAR 629 以上；Noon 则存在大量中国白牌、机翻 listing。由此确定 Jewelry V1 的商业切入区间为 SAR 99–399。

> **20–30 个真实可售 SKU。**

```text

→ 10
→ 30
→ 50
→ 100
→ 300
→ 1000+
```

区别在于：

> Jewelry 是“持续上新型目录”，不是 Aromiso 那种“大批量产品数据库”。

因此：

* 支持单商品创建
* 支持单商品发布
* 支持小批量创建
* 支持未来批量导入
* 不把批量导入作为首版核心能力
* 不依赖“商品数量达到某个数字”才能正常运行


这样才能最大程度保护 Cloudflare Free 资源。

# 十六、支付系统必须“预留高级能力”，但不自己造支付平台

这是整个项目非常重要的一条。

不要：

> 自己处理银行卡号。

不要：

> 自己写一个 Card API。

不要：

> 首版死绑 Tabby。

设计成：

```text
PaymentService
      │
      ├── CODProvider
      ├── CardProvider
      ├── BNPLProvider
      └── WalletProvider
```

Provider interface：

```text
createCheckout()
getPaymentStatus()
handleWebhook()
refund()
cancel()
```

Order 系统只关心：

```text
payment_status
provider
provider_reference
checkout_reference
amount
currency
```

不关心具体支付商。

---

# 十七、在线支付 V1 的正确策略

首版先保证：

```text
COD
```

同时：

> **保留 Hosted Checkout / Payment Redirect 能力。**

未来接：

* Stripe
* 本地 PSP
* Tabby
* Tamara
* 其他 GCC 支付服务

均通过 Payment Adapter 接入。

因此未来增加支付方式：

> **添加 provider，不修改 Order Core。**

银行卡信息不得进入自有数据库。

采用支付服务商托管收银页面/Hosted Checkout 时，站点只接收：

```text
payment session
payment status
transaction id
webhook
```

这就是本项目所谓的：

> “在线支付能力先留位置，后面通过插件/支付服务商接入”。

目前已能确认的外部生态中有 Stripe、Shopify 等连接能力，但这不意味着它们就是本项目最终支付供应商；代码必须保持 Provider-Agnostic，不允许反过来让某一个供应商决定数据库结构。

# 三十五、Cloudflare Free 约束是架构条件，不是部署结束后的监控指标

默认：

> 静态优先、动态最少。

Public：

```text

```

Dynamic：

```text

Checkout

Account

```

Workers Free 当前限制包括：

* 100,000 requests/day
* 10ms CPU/request
* 50 subrequests/request

因此：

> 不要把每一次商品浏览变成 D1 查询。

# 三十六、D1 资源保护必须内置

必须：

* 索引核心查询
* 避免 SELECT *
* 避免 N+1
* 避免无条件 COUNT(*)
* 避免首页大量实时查询
* 避免后台自动轮询
* 避免每次浏览写数据库
* 对列表 API 加上限
* 对搜索加分页
* 对统计做聚合缓存

数据库查询必须优先：

```text KV/cache
↓
Static
↓
D1
```

而不是：

```text User request
↓
D1
↓
D1
↓
D1
↓
D1
```

# 四十八、开发 AI 的最终执行原则

这是最终指令：

> **不要重新发明 Aromiso 已经成熟的基础设施。**
>
> **不要把 Aromiso 香薰业务复制过来。**
>
> **不要因为首发只有 20–30 SKU 就做一个临时的小系统。**
>
> **不要因为未来可能增加功能就提前开发所有功能。**
>
> **底层模型一次设计成长期版，首版只开启必要能力。**
>
> **Product、Order、Payment、Fulfillment、Customer 五大核心对象必须一次设计正确。**
>
> **支付、物流、WhatsApp 等外部能力全部 Provider-Agnostic。**
>
> **支付采用 Hosted Checkout / Provider Adapter 思路，不自行保存银行卡数据。**
>
> **产品采用 1→N 持续上新模型，不依赖大批量导入。**
>
> **Arabic 从第一天原生 RTL。**
>
> **所有商业数据与 Aromiso 完全隔离。**
>
> **Cloudflare Free 优先，静态优先，严格保护 Workers/D1/R2 资源。**
>
> **本文件即 Jewelry V1.0 架构基准。后续开发不得因普通需求反复改变架构。只有真实商业约束、外部支付/物流强制要求或安全问题才能触发架构修订。**
>
> **目标不是把一个“漂亮的饰品网站”做出来，而是一次建立一个以后可以持续增加产品、订单、支付、物流、内容和市场而无需推倒重来的 Jewelry Commerce OS。**
